# 从人工接力到 XSA：独立产品仓的诞生

> 整理稿，基于 2026-11-02 当日可见会话上下文与 GitHub 可核对记录整理，不是跨会话逐字原文。事实性节点均给出证据出处；证据索引见 `../evidence/2026-11-02-initialization-evidence.md`。

## 一、问题：人变成了消息队列

行途日常同时使用 ChatGPT、Claude（Personal Agent）、Codex、Claude Code、WorkBuddy 等多个 Agent。一次真实目标经常跨越多个工具：一个 Agent 出方案，用户复制给另一个 Agent 执行，再把 GitHub 链接搬回第一个 Agent 审核。每个 Agent 单独都能干活，但目标、状态、授权与回执没有贯通，用户本人成了系统里最忙的消息队列与调度器。

在自有定时任务体系的审计中，同类问题已有实证：任务登记与平台实际配置漂移、报表更新但上游快照断档、多个 Agent 对同一对象重复巡检、「运行成功」的文字提示不能证明结果正确。这些都不是模型能力问题，而是协作协议问题。

## 二、第一次落点：Event Bridge v0.1 实验

2026-11-02，xingtu-harness 仓开出实验 PR #4「Event Bridge v0.1：跨 Agent 任务协议与离线验证」（Draft）：

- SDD 定义最小任务协议（Task / Event / Receipt）、状态机与 Watchdog 规则；
- `bridge.py` 用内存模拟 content 与 code_review 两类 Worker，验证路由、幂等去重与回执指纹；
- 3 条单元测试覆盖内容路由与重复事件、审核回执 SHA、失败与审批门禁；
- 同批产出设计哲学、产品 README 草案、治理草案与 XSA Starter 三件套。

该实验明确只做离线模拟，不接入任何生产任务，也不声称能直接读写任意聊天应用。

## 三、转折：一次真实的能力差异

同日，用户希望把 XSA 从实验草案推进为独立开源产品仓。任务在 ChatGPT 对话中形成时暴露了一个结构性事实：ChatGPT 擅长规划、分析与审核，但其当前聊天环境没有创建 GitHub Repository 的接口；而 Personal Agent（Muse）具备对应的 GitHub 操作能力。

于是分工自然形成：ChatGPT 负责形成完整的任务契约（目标、迁移范围、README 要点、治理规范、交付证据格式），Muse 负责执行（核查、建仓、迁移、测试、提交），GitHub 负责保存成果与证据，最后由 ChatGPT 读取证据做独立审核。这不是演示脚本，而是真实协作中先遇到权限与能力差异，再通过专业 Agent 接力解决问题的过程。

## 四、执行中的真实波折（如实记录）

- Muse 的 GitHub 接口建仓调用返回 403（应用集成无建仓权限），第一条路径失败；改走 GitHub 网页建仓路径时，已保存的登录凭据被 GitHub 拒绝（密码不正确），第二条路径卡在登录。两条路径的失败都被如实记录，没有用「已完成」掩盖。最终建仓方式以证据页记录为准。
- 迁移取数时，GitHub 接口对较大的 Markdown 文件返回了截断内容；执行方没有直接采用截断文本，而是改从来源提交克隆并逐项核对文件大小与哈希，保证逐字节迁移。

## 五、结论与下一步

- 本案例验证的是「人工接力」层面的能力互补（`verified`）：任务契约、专业执行、证据回流、独立审核，四段都真实发生过。
- 没有验证的是「自动接力」：当前交接仍靠用户人工转发提示词。下一步按路线图推进持久化与只读适配器，再通过 Event Bridge 做自动接力的 A/B 对照（见 `../../ROADMAP.md`）。
