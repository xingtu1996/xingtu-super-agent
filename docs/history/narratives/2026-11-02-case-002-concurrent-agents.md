# Case 002：多 Agent 并发写入与授权治理

> 整理稿，基于 2026-11-02 当日 GitHub 可核对记录（仓库、分支、PR 与提交时间线）整理。事实节点均可回查；判断部分标注为小结。

## 发生了什么

2026-11-02 10:40（CST），`xingtu-super-agent` 仓建成。随后一小时内，四个 Agent 在互不知情的情况下先后向同一个新仓提交了工作：

|---|---|---|---|---|

| 11:07 | #2 | docs/dsh-superagent-fde-strategy-20261102 | 深读 DSH Super Agent 000–008 与 FDE 知识中枢立项 | 3 |

四个 PR 均为 Draft、无一合并，main 保持初始化状态。执行初始化的 Agent 在交付前做了文件级比对：四者路径互不重叠（docs/research/、incubation/ 与产品文件各行其道），合并顺序不产生文本冲突。

同一时段还发生了两起授权层面的真实摩擦：

- 建仓：API 集成无建仓权限被拒（403），网页路径中途回报互相矛盾，最终以回读事实为准完成建仓。
- 写操作审批：初始化全程每次 GitHub 写操作都触发一次人工审批卡（建分支、多次推送、建 PR 各一）；而 `.github/workflows/` 文件因集成缺少 Workflows 权限两次被拒（403），只能留待人工补齐。

## 小结（判断，非事实）

1. 这次没有冲突，靠的是各 Agent 自觉使用独立分支与 Draft PR 的纪律，不是靠机制：没有任何登记能提前回答「这个文件谁正在改」。
2. 重复执行的风险是真实的：如果两个 Agent 同时接到「初始化这个仓」的任务，按当天条件完全可能双写同一批文件。
3. 授权的粒度决定协作成本：逐次审批安全但摩擦大，永久放行省事但越界；中间地带是「一个任务批准一次限定范围」。
4. 由此形成 ADR-003：增设 Coordination Guard（所有权、租约、冲突检测、幂等、回执、安全恢复），授权走任务级限定范围，高风险动作保留逐次审批。
