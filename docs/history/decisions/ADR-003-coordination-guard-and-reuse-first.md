# ADR-003：增设 Coordination Guard；工程路线改为复用优先

- 状态：已采纳为设计（2026-11-02，用户与 ChatGPT 裁决，Muse 落档）。实现状态 `design`。
- 背景一（并发冲突）：本仓 2026-11-02 建成后一小时内，先后出现 4 个不同 Agent 的 Draft PR（研究、战略、孵化启动包、产品初始化各一）。经文件级比对四者路径互不重叠，未发生实际冲突，但这只是运气：此前没有任何机制登记「谁正在改什么」。
- 背景二（授权摩擦）：同一日，执行 Agent 的每次 GitHub 写操作都触发一次人工审批卡；建仓与工作流文件推送又分别被平台权限拒绝（403）。授权既是安全边界，也是协作成本，需要任务级、可核查的管理，而不是逐次弹窗或永久放行。
- 背景三（复用空间）：外部研究（见研究 PR #1）显示 Orca 已有实验性编排（Run / Task / Dispatch / 决策门禁 / operationId 幂等）、Orka 已有 Gateway → Inbox → Task → Worker → Outbox 的持久化协调链路、DeepSeek Harness 有插件化运行时。XSA 原计划自研的部分能力已有成熟实现可借鉴或复用。
- 决策：
  1. 架构增设 Coordination Guard，负责任务所有权、租约与心跳、冲突检测、幂等、回执核验与安全恢复（见 `../../ARCHITECTURE.md`）。
  2. 工程路线调整为：先试用 Orca 等成熟编排能力验证需求，只有真实缺口才自己开发；Orka 的事件链路列为最高优先级复用研究对象。
  3. 授权采用「一个任务批准一次限定范围」的原则：低风险、可逆、范围明确的操作争取任务级授权；删除、权限变更、公开敏感信息、生产发布等高风险动作保留逐次人工审批。平台实际提供的授权选项以执行环境实测为准，不绕过、不虚构。
  4. 安全注记：有研究指出部分 Agent 的默认启动配置包含绕过权限审批的参数，且 Git worktree 不等于安全沙箱；在真实仓库与私有工作区实验时必须启用人工审批或更严格配置，不使用默认的完全自主权限（该转述待以官方文档复核后升级为结论）。
- 影响：ROADMAP 的 v0.2 增加 Coordination Guard 原型与 Orca/Orka 复用评估两项；Event Bridge 的后续开发以缺口清单为准，不再默认全量自研。
