# 第三方案例卡 002｜多渠道数据清洗与可追溯性

- 来源：[FDE-SRC-003](../registry/SOURCES.md)，原文章含原作者渠道
- 状态：`third_party / source_claim / L1`，非行途亲历、非已复现数据管道

## 业务问题

用于舆情、竞品和营销分析的多渠道数据，会有实体命名不一、文本/音视频混杂、内容重复与父子回复关系断裂。一个错误的清洗决定可能污染多个下游报告。

## 可复用的工程模式

- **用途先行**：先明确报告使用目的、字段规则、可接受缺失率和审计要求。
- **保留原始证据**：原始数据不可逆修改须审慎；去重优先标注而不是物理删除。
- **保留关系**：每个结构化对象可追溯原帖、评论、回复及采集版本。
- **按层验证**：采集完整性、实体消歧、内容标准化、格式一致性、质量规则分别验收。
- **禁止暗改**：人工/模型修正必须留下 diff、理由与责任人。

## 最小验收样例（合成规则，未运行）

给定同一内容的 3 条转载、2 条不同账号评论：清洗后的实体聚合可识别来源相同，但仍保留 5 条原事件的各自来源 ID；无法追溯的记录进入隔离队列。此为**设计用 synthetic 示例**，并非原案例的真实数据。
